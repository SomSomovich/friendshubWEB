1. ОБЩИЕ СВЕДЕНИЯ
--------------------------------------------------------------------------------

1.1. Формат обмена
    Все запросы и ответы, если не указано иное, используют JSON:
    Content-Type: application/json
    Accept: application/json

1.2. Аутентификация
    После успешного входа клиент получает session_token. Токен передаётся
    в заголовке каждого защищённого запроса:

        Authorization: Bearer <session_token>

    Дополнительно клиент ОБЯЗАН передавать номер своего устройства, к
    которому привязана сессия:

        X-Device-Number: <device_number>

    Сервер сверяет это значение с device_number, зафиксированным в сессии.
    Несовпадение — 403 Forbidden. Заголовок опционален, но если он передан
    и не совпадает с сессией, запрос будет отклонён.

1.3. Единый формат ошибок
    Любая ошибка возвращается в виде:

        {
          "error": "<код>",
          "message": "<человекочитаемое сообщение>",
          "details": { ... }        // опционально, зависит от ошибки
        }

    Возможные значения "error":
        not_found          — объект не найден (404)
        unauthorized       — не аутентифицирован / неверный пароль / код (401)
        forbidden          — нет прав (403)
        bad_request        — некорректные данные (400)
        conflict           — конфликт состояния (409)
        rate_limited       — сработал лимит (429)
        replenish_required — у получателя почти пустой пул prekey (503)
        payload_too_large  — слишком большой объём (413)
        internal_error     — внутренняя ошибка сервера (500)

1.4. Rate limit
    Ответы с кодом 429 содержат заголовок Retry-After — число секунд до
    сброса окна.

    Лимиты по адресу клиента:
        POST /register                 — 5/мин (RATE_LIMIT_REGISTER_PER_MINUTE)
        POST /login, /login/2fa        — 10/мин (RATE_LIMIT_LOGIN_PER_MINUTE)
        POST /2fa/*                    — 10/мин
        POST /account/delete/*         — 10/мин (общий с login)

    Лимиты по аккаунту:
        GET /handles/*, POST /handles/batch    — 60/мин
        POST /attachments/init                 — 30/мин
        GET /accounts/{id}/devices             — 30/мин
        GET /accounts/{a}/devices/{d}/bundle   — 10/мин на (account, device)

1.5. Периодическая переаутентификация
    Сессия живёт SESSION_TOKEN_TTL_SECONDS (по умолчанию 30 дней).
    WebSocket-соединение проверяет валидность сессии каждые 30 секунд.
    Если сессия или устройство отозваны — соединение закрывается.

2. РЕГИСТРАЦИЯ И ВХОД
--------------------------------------------------------------------------------

2.1. POST /register — регистрация

    Запрос:
        POST /api/v1/register
        Content-Type: application/json

        {
          "password": "correct horse battery staple"
        }

    Требования к паролю: 8–128 символов.

    Ответ 201:
        {
          "id": "01923c4e-...",
          "user_id": 42,
          "fh_number": "FH1234567",
          "username": "User_1234567"
        }

    Ошибки:
        400 bad_request — пароль короче 8 или длиннее 128 символов
        429 rate_limited

--------------------------------------------------------------------------------
2.2. POST /login — вход (фаза 1: пароль)

    Запрос:
        POST /api/v1/login
        Content-Type: application/json

        {
          "fh_number": "FH1234567",
          "password": "correct horse battery staple",
          "device_number": 1
        }

    Поле device_number — номер устройства, к которому клиент хочет
    привязать сессию. Устройство должно существовать в аккаунте, кроме
    одного исключения: если у аккаунта ещё нет ни одного активного
    устройства, разрешается запросить device_number = 1 для «бутстрапа»
    первого устройства.

    Ответ 200 (2FA выключена):
        {
          "kind": "session",
          "session_token": "eY3...QK",
          "expires_at": 1799999999
        }

    Ответ 200 (2FA включена):
        {
          "kind": "totp_required",
          "challenge_token": "Lq3...mA",
          "expires_in_seconds": 300
        }

    Ошибки:
        401 unauthorized — аккаунт не найден, пароль неверен или устройство
                           не принадлежит аккаунту
        429 rate_limited — сработал лимит на аккаунт

--------------------------------------------------------------------------------
2.3. POST /login/2fa — вход (фаза 2: TOTP или backup-код)

    Запрос:
        POST /api/v1/login/2fa
        Content-Type: application/json

        {
          "challenge_token": "Lq3...mA",
          "code": "123456",
          "device_number": 1
        }

    Поле code может быть 6-значным TOTP-кодом или backup-кодом.
    Номер устройства проверяется ДО того, как код будет списан.

    Ответ 200: то же, что у /login (kind = "session").

    Ошибки:
        401 unauthorized — challenge истёк, устройство неизвестно, код неверен
        429 rate_limited — аккаунт заблокирован

--------------------------------------------------------------------------------
2.4. POST /logout — выход

    Запрос:
        POST /api/v1/logout
        Authorization: Bearer <token>
        X-Device-Number: <n>

    Ответ 204.

3. ДВУХФАКТОРНАЯ АУТЕНТИФИКАЦИЯ (2FA / TOTP)
--------------------------------------------------------------------------------

3.1. POST /2fa/enroll — начало подключения 2FA

    Запрос:
        POST /api/v1/2fa/enroll
        Authorization: Bearer <token>

    Ответ 200:
        {
          "secret_base32": "JBSWY3DPEHPK3PXP",
          "otpauth_uri": "otpauth://totp/FH:FH1234567?secret=...&issuer=FH"
        }

    Ошибки:
        409 conflict — 2FA уже включена

3.2. POST /2fa/enroll/verify — подтверждение и включение 2FA

    Запрос:
        POST /api/v1/2fa/enroll/verify
        Authorization: Bearer <token>

        {
          "code": "123456"
        }

    Ответ 200:
        {
          "backup_codes": [
            "ABCDE12345",
            "FGHJK67890",
            ...     // ровно 10 кодов
          ]
        }

    Клиент обязан показать backup-коды пользователю и не хранить их у себя.

    Ошибки:
        400 bad_request — нет отложенной регистрации 2FA
        401 unauthorized — код неверен (после TOTP_MAX_ATTEMPTS попыток
                            регистрация сбрасывается)
        409 conflict — 2FA уже включена

3.3. POST /2fa/disable — отключение 2FA

    Запрос:
        POST /api/v1/2fa/disable
        Authorization: Bearer <token>

        {
          "password": "...",
          "code": "123456"
        }

    Ответ 204.

    Ошибки:
        401 unauthorized — неверный пароль или код
        429 rate_limited — аккаунт заблокирован

5.1. POST /account/delete/initiate — начать процедуру

    Запрос:
        POST /api/v1/account/delete/initiate
        Authorization: Bearer <token>

    Ответ 200:
        {
          "confirm_after": 1799999300,
          "confirm_until": 1799999600,
          "confirm_after_seconds": 300,
          "confirm_window_seconds": 300
        }

    Клиент должен показать таймер: подтверждение доступно только в интервале
    [confirm_after, confirm_until].

5.2. POST /account/delete/confirm — подтвердить удаление

    Запрос:
        POST /api/v1/account/delete/confirm
        Authorization: Bearer <token>

        {
          "password": "...",
          "code": "123456"        // обязательно, если 2FA включена
        }

    Ответ 204. С этого момента аккаунт, все его данные и объекты в S3
    безвозвратно удалены.

    Ошибки:
        400 bad_request  — нет pending-записи или она отменена
        401 unauthorized — пароль/код неверен
        409 conflict     — ещё не пришло время подтверждения, либо окно истекло
        429 rate_limited

5.3. POST /account/delete/cancel — отменить удаление

    Ответ 204.

5.4. GET /account/delete/status — статус

    Ответ 200:
        {
          "pending": true,
          "account_id": "...",
          "initiated_at": 1799999000,
          "confirm_after": 1799999300,
          "confirm_until": 1799999600
        }

    Если удаления нет:
        {
          "pending": false,
          "account_id": null,
          "initiated_at": null,
          "confirm_after": null,
          "confirm_until": null
        }

11.6. POST /groups/{id}/members/role — выдать роль/права

    Запрос:
        {
          "target_account_id": "...",
          "role": "admin",
          "permissions": 1023
        }

    Биты разрешений (см. ALL_ADMIN_PERMS):
        1<<0  — CHANGE_PROFILE
        1<<1  — MANAGE_GREETINGS
        1<<2  — DELETE_MESSAGES
        1<<3  — BAN_USERS
        1<<4  — MANAGE_INVITES
        1<<5  — PIN_MESSAGES
        1<<6  — MANAGE_VIDEO_CHATS
        1<<7  — CHANGE_TAGS
        1<<8  — ANONYMOUS_POST
        1<<9  — ADD_ADMINS

    Правила:
        - владельца через этот эндпоинт не затронуть (403)
        - админ не может выдать бит, которого у него самого нет
        - админ не может выдать роль admin, если у него нет ADD_ADMINS

    Ответ 204.

13.1. POST /attachments/recommend — рекомендованный размер чанка

    Запрос: { "total_size": 12345678 }

    Ответ 200:
        {
          "chunk_size": 5242880,
          "chunk_sizes": [5242880, 5242880, 1860898],

        }

    Ошибки:
        413 payload_too_large — размер файла > max_file_size_mb

13.2. POST /attachments/init — начать загрузку

    Запрос:
        {
          "chunk_sizes": [5242880, 5242880, 1860898],
          "conversation_id": "...",
          "kind": "attachment"       // или "thumbnail"
        }

    Ограничения:
        chunk_count ≤ 500 (MAX_CHUNKS)
        каждый chunk ≤ 32 МиБ (MAX_CHUNK_BYTES)
        сумма ≤ max_file_size_mb
        вы должны быть участником указанного conversation

    Ответ 201:
        {
          "attachment_id": "...",
          "chunk_count": 3,
          "total_size": 12345678,
          "uploads": [
            { "chunk_index": 0, "url": "https://s3.../..." },
            { "chunk_index": 1, "url": "https://s3.../..." },
            { "chunk_index": 2, "url": "https://s3.../..." }
          ]
        }

    Клиент должен сделать PUT на каждый URL с телом соответствующего чанка.
    Content-Length должен точно совпадать с заявленным размером чанка.

    Ошибки:
        400 bad_request
        413 payload_too_large
        429 rate_limited (30/мин)

13.3. POST /attachments/{id}/finalize — финализировать

    Сервер проверит через HEAD реальный размер каждого чанка в S3, затем
    скачает его, чтобы убедиться, что он читается. При успехе вложение
    становится is_ready = 1 и uploader получает claim.

    Ответ 204.

    Ошибки:
        400 bad_request — размер не совпадает, чанк отсутствует
        403 forbidden   — вы не загрузивший
        409 conflict    — уже финализировано

13.4. POST /attachments/{id}/claim — добавить claim

    Используется при пересылке или получении. Ответ 204.

13.5. POST /attachments/{id}/release — снять claim

    Если это был последний claim — S3-объекты удаляются, запись вложения
    тоже. Ответ 204.

13.6. GET /attachments/{id} — получить presigned GET URL-ы

    Ответ 200:

22. WEBSOCKET
--------------------------------------------------------------------------------

22.1. Подключение

    URL:  ws(s)://<host>/ws
    Протокол: бинарные кадры, protobuf (схема — fh.proto)
    Максимальный размер кадра/сообщения — 256 КиБ

22.2. Порядок работы

    A. Клиент открывает соединение и в течение 10 секунд отправляет
       кадр ClientHello:
           {
             "session_token": "...",
             "device_number": 1,
             "client_name": "FriendsHub iOS/1.0"
           }

       Сервер проверяет:
         - session_token существует и не отозван
         - device_number совпадает с device_number сессии
         - устройство существует и активно
         - protocol_major совпадает с серверным (0)

    B. Сервер отвечает ServerHello:
           {
             "session_id": "...",
             "account_id": "...",
             "device_number": 1,
             "server_timestamp": 1799999000,
             "protocol_major": 0,
             "protocol_minor": 1,
             "protocol_patch": 0
           }

    C. Сервер отправляет недоставленные конверты (до 500 штук):
           { "delivery": { "envelopes": [ ... ] } }

    D. Дальнейший обмен:
       - Client → Server: Upload, Ack, Ping
       - Server → Client: Delivery, Receipt, Pong, Presence, Error,
                          BotMessage, ChannelPost

22.3. Ограничения кадра Upload

    - не более 128 конвертов в одном Upload
    - ciphertext одного конверта ≤ 64 КиБ
    - envelope_type — 1..17
    - sender_account_id обязан совпадать с account_id отправителя
    - получатель и получающее устройство должны существовать
    - при блокировке в любую сторону конверт дропается

    Кадр Receipt приходит с массивом envelope_id, успешно сохранённых.

22.4. Контроль потока

    - 100 кадров/сек — мягкий предел; 5 секунд подряд выше — разрыв
    - 30 сек интервал переаутентификации: если сессия или устройство
      отозвано — fatal-ошибка и закрытие
    - ошибка с fatal=true даёт серверу 150 мс на отправку перед закрытием

22.5. Коды ошибок в кадре Error

    unauthorized     — невалидная сессия
    device_mismatch  — Hello.device_number ≠ сессия
    replaced         — подключилось другое устройство с тем же номером
    session_revoked  — сессия отозвана
    device_revoked   — устройство отозвано
    account_deleted  — аккаунт удалён
    prekeys_low      — заканчиваются prekey (fatal=false)
    flood            — слишком много кадров
    protocol         — несовпадение major-версии
    decode           — ошибка разбора protobuf
    dispatch         — ошибка обработчика
